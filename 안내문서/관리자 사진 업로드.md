# 관리자 사진 업로드 및 3D 반영 관리

기존 Three.js + Node.js + Railway Docker 구조에 통합했습니다. 별도 Next.js 프로젝트나 데이터베이스를 만들지 않았습니다. `/admin` 또는 학교 화면의 **관리자** 링크로 엽니다.

## Railway Variables

| 변수 | 설정할 값 |
|---|---|
| `ADMIN_PASSWORD` | 직접 정하는 업로드 관리자 비밀번호, 12자 이상 |
| `OWNER_APPROVAL_PASSWORD` | 위와 다른 소유자 승인 비밀번호, 12자 이상 |
| `SESSION_SECRET` | 무작위 비밀값, 32자 이상. 32바이트를 16진수로 만든 64자 권장 |
| `ADMIN_ORIGIN` | `https://school-tour-production.up.railway.app` (끝 슬래시 없음) |
| `GITHUB_TOKEN` | 아래 비공개 사진 저장소에만 권한이 있는 fine-grained token |
| `GITHUB_OWNER` | 사진 저장소 소유자 계정명. 본인 계정 사용 시 `kh12runn` |
| `GITHUB_REPO` | 비공개 사진 저장소 이름. 공개 코드 저장소 이름을 그대로 넣지 마세요 |
| `GITHUB_BRANCH` | 사진 저장소에 이미 존재하는 브랜치 이름 (예: `main`) |
| `MAX_UPLOAD_MB` | 선택값. 기본 20, 최대 25. 파일 1장 기준 |

실제 비밀번호/토큰 값은 소스, 문서, `.env` 커밋에 넣지 않습니다. Railway Variables에서 설정하고 재배포합니다. `NODE_ENV=production`, `PORT`는 기존 Docker/Railway 설정을 유지합니다.

## GitHub 설정

1. 원본 사진용 **비공개** 저장소를 준비하고 README로 초기화하여 브랜치를 만듭니다. 코드 저장소를 비공개로 운영하는 경우 같은 저장소도 가능하지만, 공개 저장소에는 업로드를 거부합니다. 공개 `pending/` 경로는 승인 대기 사진을 비공개로 보호하지 못하기 때문입니다.
2. fine-grained token의 Repository access를 해당 저장소 **하나**로 한정합니다.
3. Repository permissions의 **Contents: Read and write**를 허용합니다. Metadata read는 기본 권한입니다. Workflows, 계정 전체 쓰기 권한은 필요하지 않습니다.
4. 토큰 만료일과 필요 시 조직 승인을 확인합니다. 선택한 사진 브랜치에 직접 커밋할 수 있어야 합니다. 강제 push는 사용하지 않습니다.
5. 사진 저장소를 Railway 코드 자동배포 소스로 연결하지 않습니다. 사진 업로드마다 학교 앱이 재빌드되지 않게 합니다.

공식 근거: [GitHub Git trees](https://docs.github.com/en/rest/git/trees), [Git references](https://docs.github.com/en/rest/git/refs).

## 사용 순서

관리자 로그인 → 건물/층/실 선택 → 사진 선택 또는 끌어놓기 → 업로드 → 소유자 인증 → 사진/개인정보 확인 → 3D 구현 승인.

- 현재 배치도 기준 본관 1~4층 + 옥상(5층), 별관 1~4층입니다. 2-1은 기존 데이터대로 **별관 4층**입니다.
- 추가 공간은 사진 분류용입니다. 방 추가/이름 변경은 기존 3D 구조나 교실명을 자동 변경하지 않습니다.
- 소유자는 이름 수정 및 사진 없는 추가 공간의 목록 숨김(삭제)을 할 수 있습니다. 원래 공간/사진 있는 공간/원본 파일은 UI에서 삭제하지 않습니다.
- 기존 6-4/6-6/2-1 및 교장실은 기존 구현 표시를 따로 제공하며, 새 시스템에 사진이 업로드된 것으로 꾸미지 않습니다.
- 일반 관리자 세션 4시간, 소유자 승인 권한 30분. HttpOnly/SameSite=Strict, 운영 환경 Secure 쿠키. 로그아웃 시 서버 세션 폐기.
- 세션과 속도 제한은 서버 메모리에 있습니다. **Railway 인스턴스 1개**로 운영합니다. 재시작 시 재로그인이 필요하며, 여러 인스턴스로 확장하려면 공유 세션/제한 저장소를 추가해야 합니다.

## 저장 및 상태

```
school-assets/
  catalog.json
  uploads/
    별관/4층/4F_2-1/
      manifest.json
      고유시각_UUID.png
```

원본 이름은 메타데이터에만 기록하고, 저장 파일명은 매번 고유하게 생성합니다. 각 사진에는 `approval: pending | approved`가 있습니다. 실의 `status`는 `unshot → pending → approved → in_progress → completed`입니다. 화면의 ‘사진 업로드됨’은 저장 성공 안내로 표시하며, 업로드 직후에는 승인 대기로 전환합니다.

사진과 실 manifest 및 catalog는 한 Git tree/commit으로 게시합니다. 중간 실패 시 사진만 목록에 등록되거나 목록만 등록되지 않습니다. 동시에 다른 커밋이 생기면 최신 브랜치를 다시 읽어 최대 3회 재시도하며 기존 커밋을 강제로 덮어쓰지 않습니다.

새 사진을 추가하면 그 사진들만 pending입니다. 이미 승인된 사진은 계속 읽을 수 있고, 새 사진은 다음 승인 전까지 공개 API에서 제외됩니다. 소유자는 본 사진 목록의 revision이 최신일 때만 승인할 수 있습니다. 승인했다고 파일을 복제/이동하지 않습니다.

## 3D 연결 (자동 생성 아님)

- `GET /api/rooms/4F_2-1/assets`: 승인된 사진만 반환.
- 응답: 기존 공간 ID, 건물/층, Blender 좌표계 bounds, 이미지 URL/크기/유형, 빈 hotspots, `requiresManualMapping: true`.
- `window.schoolTour.getApprovedAssets('4F_2-1')` 또는 `웹학교/승인사진자료.mjs`로 명시적으로 읽을 수 있습니다.
- 신규 사진은 기존 6-4 사진 UV, 360 뷰, 카메라, 가구, 충돌, hotspot을 자동으로 바꾸지 않습니다. ‘별관 4층 2-1 구현해줘’처럼 별도 요청 후 구현자가 승인된 자료를 확인하고 수동으로 연결합니다.
- 2:1 이미지는 360 **후보**일 뿐입니다. 실제 equirectangular 여부/방향/UV/hotspot 좌표는 추가 확인이 필요합니다.
- ‘구현 중/완료’ 버튼은 업무 상태만 바꾸며 모델을 만들거나 배포하지 않습니다.

## API

| 요청 | 용도/권한 |
|---|---|
| `GET /api/admin/session` | 로그인 상태·CSRF·용량 한도 |
| `POST /api/admin/login` | 관리자 로그인 |
| `POST /api/admin/owner-login` | 관리자 세션을 소유자 승인 권한으로 승격 |
| `POST /api/admin/logout` | 세션 폐기 |
| `GET /api/admin/structure` | 기존 공간 + 추가 공간/사진/상태, 관리자 |
| `GET /api/admin/pending` | 승인 대기 목록, 관리자 |
| `POST /api/admin/upload?roomId=...` | 이미지 원시 body, 관리자 |
| `POST /api/admin/approve` | roomId/revision/privacyConfirmed, 소유자 |
| `POST /api/admin/status` | 구현 진행 상태, 소유자 |
| `POST /api/admin/rooms` | 추가(관리자)/이름 수정·빈 추가 공간 숨김(소유자) |
| `GET /api/admin/rooms/:id/images/:imageId` | 원본 검토, 관리자 |
| `GET /api/rooms/:id/assets` | 승인 자료 목록, 공개 |
| `GET /api/rooms/:id/assets/:imageId` | 승인 이미지, 공개 |

쓰기 API는 같은 사이트 Origin과 세션 CSRF 헤더가 필요합니다. upload는 `Content-Type: image/jpeg|image/png|image/webp`, `X-File-Name: encodeURIComponent(원래 이름)`, `X-CSRF-Token`을 사용합니다. API에는 GitHub 토큰/비밀번호를 돌려주지 않습니다.

## 용량·보안·한계

- 사진 1장씩 전송·저장하여 서버의 대용량 처리 동시성을 1로 제한합니다. 다른 관리자가 업로드 중이면 429와 재시도 안내가 나옵니다. 클라이언트도 순차 전송하고 실패한 파일은 계속 표시합니다.
- 임시 파일은 Railway의 일시 디스크에만 쓰고 요청 종료 후 제거합니다. 개발 PC로 사진을 복사하지 않습니다. GitHub base64 API 특성상 저장 단계에 파일 1장 크기의 제한된 메모리 사용이 발생합니다. 스트리밍 끝까지 무복사를 보장하는 방식은 아닙니다.
- 기본 파일당 20MB, 최대 25MB, 20,000px/축 및 1억 2천만 화소 이하, 공간당 100장, 클라이언트 한 번에 30장. catalog 900KB 한도를 넘으면 분할 저장소/객체 저장소 전환이 필요합니다.
- 확장자/MIME/바이너리 시그니처/크기/해상도를 검사합니다. SVG·HTML·INSP·영상·HEIC는 거부합니다. 완전한 악성코드 검사나 이미지 재인코딩 서비스는 아닙니다.
- 로그인 반복 실패, API 호출, 쓰기, 업로드에 속도 제한을 적용합니다. 운영 환경은 정확한 HTTPS `ADMIN_ORIGIN`이 필요합니다.
- 승인 전 원본은 관리자만 검토할 수 있지만, **승인 후에는 사진이 공개 API로 제공됩니다**. 얼굴, 이름표, 연락처, 게시물 개인정보, EXIF 위치정보 등을 먼저 제거하고 소유자가 확인해야 합니다. 이 기능 자체는 인물 제거를 하지 않습니다.
- 사진을 영구 보관하는 Git 저장소는 이력까지 용량이 늘어납니다. 대규모 장기 운영은 객체 저장소가 더 적합할 수 있습니다.
- 네트워크 끊김/시간 초과 시 GitHub 저장은 이미 끝났을 수 있으므로 재업로드 전 저장 목록부터 확인합니다.
- 관리자 기능 환경변수가 없으면 관리자 로그인을 차단하고 기존 학교 탐험/healthz는 계속 동작합니다.

## 검사

`node 웹학교/검사/관리자검사.mjs`: 잘못된 로그인, CSRF/Origin, 원본 비공개, MIME/경로/용량, 업로드/manifest, 같은 이름, 동시 요청, Git 커밋 충돌 재시도, 부분 실패, 소유자 승인/이전 revision 거부, 상태, 공간 관리, 공개 저장소 거부, 로그아웃/만료/속도 제한.

GitHub 쓰기 검사는 **실제 REST 어댑터 + 메모리 내 GitHub 계약 모형**입니다. 실제 GitHub 토큰/비공개 저장소를 연결한 원격 실증은 운영 설정 후 별도 확인해야 합니다. 가짜 저장소나 테스트 자격증명은 운영 패키지에 포함하지 않습니다.

`node 웹학교/검사/배포검사.mjs`: 실제 배포 패키지의 서버를 실행하여 정적 자산·압축·관리자 화면·비공개 경로 차단·healthz를 검사합니다. 로컬 Docker daemon이 꺼져 있으면 Docker 이미지 빌드 검사는 Railway 빌드에서 확인합니다.
